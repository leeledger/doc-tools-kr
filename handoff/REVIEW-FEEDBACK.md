## Should Fix
- src/tools/pdf-to-jpg/controller.ts:280-290, 232-248 (confidence: 7) — Double submit on the password form starts two `openPdf` calls. `unlock()` gates on `state !== 'locked'`, but `openWith` leaves the state at 'locked' until pdf.js answers, so Enter pressed twice runs two attempts with the same `runId`. If both succeed, `opened = o` (line 248) overwrites the first document without closing it, and its pdf.js worker memory leaks. This also breaks "one attempt per click" (brief decision 13 spirit). Fix: a `let unlocking = false` guard (or disable the submit button / move to an 'opening' state) for the length of the attempt; before `opened = o`, close any previous `opened`.
- src/tools/pdf-to-jpg/controller.ts:342-357 (confidence: 6, verify) — The early `return` at line 343 is inside the `try`, so a stale run's `finally` still runs `renderTask = null`. Sequence: cancel → the old loop is still waiting in `await doc.getPage(p)` → the user presses 변환 again → the new run sets `renderTask` → the old loop wakes up, returns, and its `finally` sets the new run's `renderTask` to null. The next cancel then cannot stop the page that is drawing (runId still stops the run after that page, so only the response is late). Fix: in the `finally`, `if (renderTask === task) renderTask = null`, or check `id !== runId` before creating the canvas and before the `try`.
- src/tools/pdf-to-jpg/output.ts:32-36 (confidence: 7) — The "Blob parts" are raw `Uint8Array` chunks kept on the JS heap until `finish()`. `new Blob(this.parts)` then copies them, so peak memory is about twice the ZIP. On PC, 500 pages at 300 ppi can mean several hundred MB of JPEGs. The page caps limit this, and the brief's wording is met. Cheap improvement: push `new Blob([chunk])` per chunk (or fold the parts into one Blob every ~32 MB) so the browser can keep the bytes outside the JS heap and the final Blob does not double them.
- src/tools/pdf-to-jpg/controller.ts:371 (confidence: 6) — pdf.js errors from `getPage`/`render` on a damaged page (InvalidPDFException, UnknownErrorException, FormatError) have no `code: 'corrupt'`, so they fall through to 'unknown' ("새로고침 후 다시 시도"). Map them by `name` the way inspect.ts does on open, so the user gets the 손상 message and the usage code is right.
- Open question (no ppi stamp) — Agree it is a gap, not a blocker. Chrome/Safari canvas JPEGs start with a JFIF APP0 header. Writing units=1 and X/Y density = ppi at fixed offsets (after checking the `JFIF\0` marker) is about 10 lines and a unit test, if Arch wants it now. It matters for people who print the JPGs (Word/HWP insert them at 96 dpi size otherwise).

## Escalate to Architect
- Owner-restricted PDFs convert silently (Bob's open question). pdf.js ignores the owner permissions, so a PDF that forbids copying/printing comes out as plain JPGs. That is close to the "restriction removal" the brief rules out for T4 (decision 13). Options: (a) leave it silent (current); (b) a neutral one-line note when `doc.getPermissions()` returns restrictions; (c) refuse. This is a product/legal call, not a code one.
- Precache headroom for T4. Production (default build, plus the Naver meta tag on each precached page) is at 441.7 KB, so T3 itself is not a CI risk: CI's cloud build uses the same env Bob used locally, and the measure is deterministic. But the cloud build is at 448.1 / 450 KB, and Bob's plan ("T4 starts in NOT_PRECACHED") does not cover it. A new live tool still adds its name and link to every precached page (home list, nav/QuickLinks, description) and may add glyphs to the precached UI font subset. Those bytes land on pages that ARE precached, so 1.9 KB is likely gone in T4 even with /pdf-password/ excluded. Arch should decide before T4 starts: either drop another page from the precache now (for example /hwp-viewer/ or /stamp-signature/ in the cloud build), or approve a different budget rule. The limit is "never raised", so this has to be a ruling.
